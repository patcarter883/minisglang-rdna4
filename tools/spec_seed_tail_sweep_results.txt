RESULT 2 — THE TAIL SIZE IS NOT THE LEVER. Two independent proofs.
  (a) SHORT is BIT-IDENTICAL for every tail in {32,64,128,256,528}: same completion md5 (f6a4727c),
      same step count (71), same accept-len (5.394), same per-step P-bucket table, same first draft
      chain `[3316, 268, 2258, 444, 8244, 96, 268, 160, 458, 268, 78, 458, 268, 458, 268]`, in BOTH
      replicates. Above 32 trailing positions the knob changes nothing on a 95-token prompt.
      (The knob IS live: at 3571 tokens the first draft chain differs between every tail — t32/t64/
      t128/t256/t528 diverge from draft position 4 onward — so this is model behaviour, not an
      inert code path.)
  (b) LONG differences are the greedy CONTENT LOTTERY, not the knob. Restricting accept-len to the
      region where the seed can still be inside the drafter's fixed 512-key window:

      On the LONG prompt the seed produces NO lift, in either replicate, in the only region where it

RESULT 3 — THE CROSSOVER IS REAL AND IT IS AT ~400-600 PROMPT TOKENS
  First attempt (tools/spec_seed_crossover.sh) TRUNCATED the code prompt to intermediate lengths.
  **VOID as a length measurement**: each truncation asks for a different continuation, and accept-len
  swung 3.0-8.0 *within one leg* (P297=7.984 vs P554=4.088 at tail=0), with the two legs disagreeing
  in sign at 4 of 6 lengths. Recorded so nobody re-runs it.

  tools/spec_seed_padlen.sh fixes the design: the SAME 95-token B-tree instruction is always the LAST
  thing in the prompt, preceded by N tokens of filler from the code file. The requested output is
  constant; only the number of prompt tokens in front of the task moves. One boot per leg,
  max_tokens=384, longest-first so the shared filler prefix is a radix hit.

    prompt_tok | PLAIN tok/s | tail 0 acc / tok/s | tail 64 acc / tok/s | seed effect on accept-len

  The seed's advantage decays MONOTONICALLY over 95 -> 223 -> 351 (+23.9 -> +16.1 -> +10.7%) and is

  system that could put it there. n=1 per cell, so read the 607 cell's -14.3% as scatter around zero,
  not as a dip.

RESULT 4 — WHAT THIS DOES TO 341c4df0's EXPLANATION
  341c4df0 blamed the 528 regression on EVICTION: "a window-sized prompt seed evicts the model's own
  recent output for ~500 generated tokens". **That mechanism is falsified by this sweep.** A 32-token
  seed can evict at most 32 of 512 keys, yet tail=32 is not better than tail=528 on the LONG prompt
  (mean accept-len 4.019 vs 4.101, both below tail=0's 4.479) and is bit-identical to it on the SHORT
  prompt. Size is not what is happening. What IS happening is that the seed's value is a function of
  PROMPT LENGTH (Result 3) and dies at the drafter's window — a 64-token summary of a 3.5k-token code
  file is not a substitute for the code file, however you slice it.
  The original A/B's headline (-15.6% accept-len at tail=528 on the long prompt) also does not
  survive replication as a *seed* effect: measured again here across 2 boots, 528 is -8.4% against
  tail=0 while tail=0 itself spans 19% boot-to-boot.

VERDICT / CHOSEN DEFAULT — `_SEED_TAIL_DEFAULT = 64`, UNCHANGED, now measured rather than provisional
  Decision rule as specified: must not regress the LONG prompt below plain decode, then maximise
  tok/s across both regimes.
    * Gate (every LONG leg above its OWN boot's matched plain leg, 4/4): passed by tail 0 and
      tail 64 ONLY. tail 32 fails rep1 (62.54 vs plain 64.19); tail 128 fails rep2 (62.41 vs 64.16);
      tail 256 fails rep2 (64.02 vs 64.16); tail 528 fails rep2 (64.12 vs 64.16).
    * Of the two survivors: LONG 75.39 (tail 0) vs 73.55 (tail 64) — tail 0 by +2.5%, inside the
      measured 19% lottery band. SHORT 84.32 vs 101.11 — tail 64 by +19.9%, reproducible to <1%.
      Combined 79.73 vs 86.23.
    * 128 ties 64 on the combined score (86.36 vs 86.23) but fails the LONG gate and has 4x the
      spread (LONG legs 62.41-86.11 vs 64's 70.02-77.26). 64 is the pick.
  NO SINGLE TAIL WINS BOTH REGIMES, and this is the honest cost: **choosing tail=64 over seeding-off
  costs the long-prompt regime about 2.5% of tok/s (73.55 vs 75.39, not resolvable against a 19%
  lottery band) to buy the short-prompt regime 19.9% (101.11 vs 84.32, reproducible).** Seeding-off
  is NOT simply best at long prompts — it is 0-3% better there, which is under the noise floor — so
  the "ship it off" outcome is not what the data says. It says the tail number is irrelevant and the
  feature is worth having for prompts up to ~500 tokens and free-but-pointless above that.

NEXT (do not guess — this is the measured follow-up)
  Make the seed PROMPT-LENGTH GATED: seed when the prompt is <= the drafter's sliding_window (512),

  and give back the 0-to-3% the long regime pays. That is a scheduler-side predicate on
  `prefill_aux_tail`, not a new tail value, so this sweep cannot pick it — it needs its own A/B.
