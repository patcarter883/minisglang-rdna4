# CPU MoE tier on NVFP4 e4m3 — results, 2026-09-07

## 1. Numerics — PASS (this is the part that is finished)

Real checkpoint bytes, layer 0, TP=2 rank-0 shard, 16 experts, top-10, 4 tokens.
`tools/cpu_moe/validate_so.py --policy e4m3 [--gpu]`.

| measurement | value |
|---|---|
| CPU tier (`vnni_nvfp4_e4m3_g16`) vs float64 oracle | **8.371558e-03** |
| CPU tier vs its own int8-activation twin (arithmetic only) | **2.846829e-07** |
| GPU `w4a8_moe` vs the SAME float64 oracle | **3.952644e-02** |
| CPU tier vs GPU path | 4.048232e-02 |
| CONTROL: per-channel global dropped | **5.574821e+11** |
| fp16 comparand policy, unchanged | 2.743434e-07 |

The CPU tier is **4.7x more accurate than the device path it offloads from**, and reproduces the
repo's recorded 8.3e-03 / 4.1e-02 pair.

e4m3 scale-byte census on the served tensors: 2,457,600 bytes, range 0x4A..0x7E, **0** outside the
positive-normal range the fast decode assumes.

The second scale level is a per-OUTPUT-CHANNEL vector, not a scalar, and this checkpoint hides that:
`w13`'s global is constant across all 640 channels (2.078102e-04), so a scalar would have produced a
CORRECT gate_up and a wrong down_proj (`w2` spans 2.488636e-05..1.947312e-04) — half the layer right.

## 3. Two BLOCKING bugs found. One fixed, one diagnosed.

### (A) FIXED — `StageASession.enabled` ignored the CPU tier
`enabled` was `host_bytes > 0`, and `host_bytes` counts only the PINNED arena. A CPU-tier layer needs
no pinned memory, so an all-CPU plan reported `enabled=False`; `Engine._load_weight_chunked` gates on
it, so the plan that needs Stage B most got the ONE-SHOT loader, which materialises expert stacks on
the DEVICE. It OOM'd at 15.54/15.92 GiB allocating a 400 MiB stack.

After the fix, at `--weight-offload-cpu-layers 48`:
    weight offload: weight-arena=0 MiB host=0 MiBx2 [0/0 layers device, f=0.000]
    arena attached, 0.00 GiB planned ; arena reservation: chunks=0 reserved=0 B fill=0.0%
The pinned tier is genuinely EMPTY and Stage-B chunking is on the path.

### (B) DIAGNOSED, NOT FIXED — TP-overlap deadlock, CPU tier only
Reproduced at 2, 12 and 48 CPU layers. Never at 0.

Evidence (`WEDGE_TP_OVERLAP_2026-09-07.txt`), both ranks, 5 samples over 12 s, identical:
    _ep_route (layers/moe.py:1206)          <- torch.topk
    forward (layers/moe.py:1331)
    _fused_partial (models/qwen3_5_moe.py:113)
    rowchunked_ar_span (layers/tp_overlap.py:401)
rocm-smi at the wedge: GPU[0] 3% / 22 W (idle), GPU[1] 100% / 56 W. Both CPU-MoE worker threads
IDLE in `queue.get` — the CPU tier is not what is hanging. No error, no traceback; `gpu-lease`
eventually kills it with exit 76 ("kernel never returned").

MECHANISM: `rowchunked_ar_span` splits token rows into chunks and runs async all-reduces on a SIDE
STREAM. Inside that region `_fused_partial` reaches the CPU branch, and `cpu_submit` does
`hidden_states.detach().to("cpu", copy=True)` — a blocking host/device sync in the middle of a
chunked async-collective region. The ranks desync and the collective never completes.

Why it is CPU-tier-exclusive: `moe.py:1331` is the ONLY caller of `_ep_route`. The GPU path hands raw
`router_logits` to `kernels.w4a8_moe`, which routes INTERNALLY — so `softmax`+`topk` in Python are
never executed on the served GPU path.

UNTESTED FIX to try first: `MINISGL_TP_OVERLAP=0` (now plumbed through docker-compose). If that
serves, the structural fix is to take the plain-all_reduce path for any layer the CPU tier computes,
rather than to disable overlap globally.
