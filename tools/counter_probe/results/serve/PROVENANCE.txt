per-tensor fp8-KV scales -> per-head. MINISGL_KV_FP8=0 does NOT avoid it (the call signature changed,
not just the dtype policy), and MINISGL_TAIL_HIP=0 does avoid it but swaps the HIP tail for a torch

What `lean-prof` actually was, discovered by diffing the two images: TWO things, both needed.
  1. torch/lib/librocprofiler-sdk.so symlinked to /opt/rocm/lib/librocprofiler-sdk.so.1. Torch's
     vendored copy registers after rocprofv3 closes its configuration window -> core dump in
     rocprofiler_configure.
  2. LD_LIBRARY_PATH=/opt/rocprof-deps. Without it the rocprofv3 LD_PRELOAD cannot resolve libdw, and
     because the preload applies to every exec in the container the first casualty is /usr/bin/env:
       /usr/bin/env: error while loading shared libraries: libdw.so.1: cannot open shared object file
     The library is PRESENT in both images, merely unreachable — it reads as a missing package and is
     not one.

BOTH legs run this SAME image. Running the control on stock `lean` would have compared a wall measured
on one kernel package against busy time measured on another.

CONC=8 does NOT boot on this pair — engine.py::_determine_num_pages asserts
"Not enough memory for KV cache after reserving recurrent state / draft model / CUDA-graph buffers".
This is a GDN HYBRID: 30 of its 40 layers hold a per-sequence recurrent state reserved up front for
max-running-requests, so max-running trades against the KV pool far more steeply than on a dense-KV
model. 4 @ 0.86 boots. Reported concurrency points are therefore M=1 and M=4, not M=1 and M=8.

Scheduler loop actually taken: normal_loop (NOT overlap_loop). `gdn_radix=True` makes
snapshot_kind == "recurrent", and run_forever forces the synchronous non-overlap loop when
_rec_radix is set. Confirmed in the engine log ("Reserved 0.32 GiB for the recurrent-radix snapshot
store"). The ROCTx ranges in the trace are named normal_step#<n>.

METHOD
------
* Busy = UNION of kernel intervals, per AGENT (= per card), clipped to the marker window. The naive
  SUM is reported beside it so the double-count is visible rather than assumed away.
* Wall = the CONTROL leg's median inter-token gap. NOT the marker-derived wall, and not the profiled
  run's mean — see "the instrument" below.
* Step boundaries come from ROCTx ranges named normal_step#<iteration>, one per scheduler-loop
  iteration, emitted by the new scheduler.py::_rtx_step_begin. rocprofv3 stamps marker and kernel
  records from the same clock, so they are directly comparable.
* Windows are placed by loop-iteration index; the driver's phases have fixed token counts
  (ignore_eos + max_tokens) so that index is deterministic.

THE INSTRUMENT — why the marker-derived wall is NOT the answer
--------------------------------------------------------------
Marker wall/step inside the collection window was 61.445 ms (bs=1) and 82.468 ms (bs=4), against a
true 10.970 / 15.767 ms. rocprofv3 recording ~1200 dispatches per step costs ~50 ms/step, and it lands
entirely in the INTER-KERNEL GAPS (host-side dispatch interception), not inside kernel execution.

This is visible in the profiled driver's own numbers: phase A's median gap was 11.306 ms while its
mean was 28.008 ms — the ~400 steps outside the window ran at the true ~11 ms and the 200 steps inside
it ran at ~61 ms. The control leg then confirms it independently: 10.970 ms median with p10-p90 of
10.8-12.0 ms, a tight steady state with no such tail.

Direction of any residual error is safe for the conclusion: if the profiler inflated kernel DURATIONS
at all, busy would be over-stated, so the true idle fraction would be even LOWER than reported here —
i.e. further from "68% idle", not closer.


VERDICTS
--------
Claim 5 "bs=1 decode is inter-kernel-gap bound, ~68% idle"
  REFUTED, and close to inverted. Measured 28.8 % idle / 71.2 % busy at bs=1 on a real serve.
  The 68 %-idle figure is consistent with a torch-profiler-derived number, which this workload
  inflates ~3x (the repo's own recorded trace reports 35.3 ms GPU-busy against a real 11 ms step).

Claim 4 "serving is overhead-bound, memory controller <=27% at every batch size"
  DIRECTIONALLY RIGHT, FIGURE SLIGHTLY LOW. Measured 31.5 % (bs=1) and 31.1 % (bs=4) of the 706.6
  GB/s roofline. Nowhere near bandwidth-saturated at either batch size, so "not bandwidth-bound"
  holds; "<=27%" does not, on this model at these two points.
  Note the two claims do not compose the way they are usually used together: the step is NOT
  idle-dominated (28.8 % idle), yet bandwidth is still only 31 %. Even counting ONLY the time kernels
  are executing, the GPU reaches just 44.3 % (bs=1) / 40.6 % (bs=4) of HBM. The gap is inside the
  kernels, not between them.


NOT ESTABLISHED
---------------
* M=8. The engine will not boot at max-running-requests=8 on 16 GB cards for this GDN hybrid, so
  "at EVERY batch size" is tested at two points (1 and 4), not across a sweep.
* rank1 / card 1. Only rank0's process was traced; the busy numbers are one card.
* Whether rocprofv3 perturbs individual kernel durations was not measured directly, only bounded by
  its direction (see above).
* SPEC=none only. The MTP spec-decode step has a different kernel mix and is not covered here.
