  The seed IS reaching the drafter, and the cleanest proof is not the bucket table but the FIRST
  DECODE STEP: baseline logs `P=0 k=0 n=0 emitted=1 draft=None` — it cannot draft at all, its aux
  is empty — while the candidate logs `P=0 k=15` with a real 15-token chain. Immediate-divergence
  probability P(n=0) on the code prompt drops 0.162 -> 0.051.

  But the low-P buckets move by +8 to +21%, NOT from ~3.5 to ~7.4. The starvation reading of §11.5
  is therefore FALSIFIED as a causal account: filling the drafter's window with prompt hidden states
  does not buy the acceptance that the same window filled with the model's own generated tokens
  buys. P does not index "window occupancy"; it indexes "how much of the window is the model's own
  recent output". A 528-position prompt seed EVICTS that output from a 512-wide window for the first
  ~500 generated tokens, which is why the long-prompt legs get WORSE overall while the 95-token
  prompt (which cannot evict anything — the whole seed fits well inside the window alongside the
  generated tail) gets better.

  Indexing was checked and is NOT the bug: the seed is the tail ENDING at the prompt's last
  position and the consumer derives ctx_start = cached_len - P, so absolute RoPE positions line up
  (scheduler.py:2318-2322, spec/dflash.py:552-554).

  tag    BASELINE   CANDIDATE  PLAIN      verdict
  warm   282b24cb   4b7727b1   282b24cb   base==plain, cand differs

  CONTROL 1: BASELINE spec already differs from PLAIN on CODE1, CODE2 and SHORT. Spec-vs-plain byte
             identity is NOT a property of this build/config, so a base-vs-cand difference is not
             evidence that seeding corrupts the verify path.
  CONTROL 2: PLAIN CODE1 (219b2448) != PLAIN CODE2 (99922ba7) — the SAME prompt, SAME boot,
             temperature 0, spec ENTIRELY OFF, and the text still differs across the radix
             prefix-cache hit. And BASELINE CODE1 differs between its own two boots (0191b4f3 vs
             1e9f7b94). The engine is not byte-deterministic here at all.
  Cause is the production config, not spec: fp8 KV quantisation (MINISGL_KV_FP8=1) makes the KV a
  function of how many positions are written per step, and the SWA-radix ring reuse changes it
  again on a hit. §11's exact reproductions were all at MINISGL_KV_FP8=0.
  VERDICT: no losslessness violation can be attributed to the seed, and none is demonstrable in
  either direction on this config. Anyone wanting a real byte-identity gate must run it at
  MINISGL_KV_FP8=0 with the prefix cache cold.
  COHERENCE: read on every leg. All legs produce coherent, on-task, correctly-referencing code
  (they cite the actual RotaryEmbedding / RMSNorm classes from the pasted files). No degradation.

BOTTOM LINE
  Seeding did NOT lift acceptance where the diagnosis said it would. On the workload the change was
  built for — a 3.5k-token real code prompt — it costs 15.6% accept-len and 12% tok/s and gives back
  the whole spec-decode win. It helps, by +22% accept-len / +13-20% tok/s, only on a SHORT prompt,
  where the seed fits inside the drafter's window without evicting generated context.
  DO NOT SHIP AS AN UNCONDITIONAL DEFAULT.
  The one obvious follow-up, cheap and directly implied by the sign flip: sweep
  `prefill_aux_tail` DOWN (528 -> 128 -> 64 -> 32). The measured pattern predicts the long-prompt
  regression shrinks and probably turns positive as the seed stops evicting the generated tail —
  i.e. the right amount of prompt context is a small one, not a window-full.
