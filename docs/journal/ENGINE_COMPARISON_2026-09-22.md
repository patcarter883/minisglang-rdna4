# minisgl vs. the checkpoint author's vLLM fork — HIP kernels and serving pathways

*Static read only. No GPU was used, no lease taken, no benchmark run; the live `tcvllm` container was never touched (all reads were `docker run --rm` off the same image). Every timing/capacity figure below is quoted from a committed doc, a source comment, or a checkpoint header, and is labelled as such. Where a finding and its adversarial verdict disagree, the verdict wins and I say so.*

---

## 1. The shape of the difference

Two teams wrote native gfx1201 HIP kernel sets for the same checkpoint on the same silicon, and the convergence is as striking as the divergence: identical GDN math down to the DS conv layout and the bf16 SSM cache, identical QSA indexer semantics (score, compression order, group-RoPE position, `budget + r - 1` width), the same head-size set {64,128,256,512}, the same page-16 KV granularity, the same exp2 softmax fold, the same lifted vLLM Triton `unified_attention` at 64 segments as the escape hatch, the same decision to hand-write rather than use rocWMMA/aiter/CUTLASS, the same gate|up stacking and block-aligned `sorted_ids` MoE routing contract, and — independently — the same capture-safety fix (a kernel policy must never be inferred from a shape that differs between capture and replay) and the same discovery that ROCm's host-registered pages are HMM userptr and need an explicit `mlock()`. None of that is where the answers are.

At the **kernel layer** the philosophies invert. They decompose and specialize: a GDN prefill split into five kernels with bf16 global intermediates, three forked MoE GEMM families, a per-geometry hipRTC-compiled KV writer, an attention op whose geometry arrives as *integer arguments* with a launcher-side law. We fuse and template: one GDN mega-kernel carrying a 62 KB LDS state arena, one `WLoad`-templated grouped MoE core covering seven weight formats, one decode kernel doing conv + recurrence + gated RMSNorm, 12,284 compiled instantiations against their 1,312. Their design buys occupancy and a small, auditable binary; ours buys launch-leanness, format reach, and a single place where an optimisation lands. Two structural gaps are ours: they have HIP kernels for things we still run in torch (the PLE dilated short conv, the recurrent state migration, batched multi-pointer copies, a persistent HyperConnection megakernel), and their collectives PUSH where we PULL.

At the **serving layer** the split is about who is the residual claimant on VRAM and where recurrent state lives. They plan before loading — a safetensors-header census, a hand-fitted per-architecture overhead registry, an analytic cudagraph fit — reserve KV for one max-length request +8%, hand the remainder to the expert cache, and hard-cap KV at that modelled reserve. We measure after loading and let the KV pool be the remainder, deriving servable context from the pool we got. They make each recurrent state a hashed, ref-counted block in the shared KV pool (which forces their attention block up to 1600 tokens); we keep it as an opaque clone in a pinned host arena attached to radix nodes (16-token match granularity, ~17 MB/snapshot off the card). That single choice is why they run overlapped async scheduling on this model and we force the synchronous loop. On a 16 GiB card our philosophy is the better one — but theirs derives the KV/expert split with no operator input, and ours cannot boot an offloading serve without a hand-picked `--weight-offload-device-gb`.

## 3. Serving pathway differences (the decisions)

**Memory planning — residual claimant.** Theirs: `expert_plan.build_plan` computes `fixed = non_expert + kv_reserve + graphs + overhead`, `room = budget - fixed`, `total_slots = room // expert_bytes`, all at config time from a safetensors header census and a hand-fitted per-architecture registry (`_qwen4exp_overhead` = 5.25 GiB + 0.22 GiB/1024 tokens; KV bytes/token a `{2: 8040, 4: 11041}` table). `maybe_auto_enable_expert_offload` turns offload on by itself. Ours: `engine.py:1894` measures the model as a free-memory delta and subtracts seven named terms; `_weight_offload_device_budget` (`engine.py:1671-1725`) hands the expert tier the *whole* `total × memory_ratio`, which is why `bake.py:1395` has to refuse a derived budget outright. Their registry was fitted on 32 GiB R9700s; on our 16 GiB cards the committed baseline (`docs/journal/Q4E_MXFP4_BASELINE_2026-09-22.md`) records their KV figure 13.3% low and overhead 1.2 GiB high.

**KV sizing direction.** For them `max_model_len` is an input they hard-cap KV against (`gpu_worker.py` FORK-LOCAL clamp to `kv_one_request × 1.08`), so a modelling error kills the boot ~5 minutes in with 1.77 GiB of headroom free, and lowering `max-model-len` provably cannot fix a proportional shortfall. For us it is an *output*: `engine.py:691` `max_seq_len = min(config.max_seq_len, num_tokens)`, and `scheduler.py:1613-1626` rejects an over-long request with an explicit ack. Ours degrades context instead of refusing.

**Hybrid prefix caching.** Theirs: GDN state and the PLE short-conv window are each a `MambaSpec` KV-cache group; a state checkpoint is a hashed, ref-counted, LRU-evicted block. Price: `platforms/interface.py` raises the attention block until an attention page ≥ a mamba page — **1600 tokens on this box** — so `hash_block_size` is 1600, a 1500-token follow-up turn gets zero reuse, and `_mamba_block_aligned_split` quantizes a continuing 4096-token prefill chunk to 3200. Ours: an opaque `rec_state` clone in a pinned host arena on the radix node, 16-token granularity, at most 15 tokens of chunk loss. Both engines independently arrived at the same invariant — clip a non-final prefill chunk to a boundary where recurrent state is actually cacheable (`scheduler/prefill.py:122-128` vs their `_mamba_block_aligned_split`).

**Scheduling.** They run async/overlapped scheduling on this exact model: the token pipeline is device-resident (`post_update` writes sampled tokens into `all_token_ids.gpu` on-stream), the n-gram context is a device gather, and the async scheduler defers the prefix-cache commit by `num_output_placeholders`. We force `normal_loop()` whenever `_rec_radix or _swa_radix or _ple` (`scheduler.py:1342-1354`) — and on the shipped q4e arm `_rec_radix` alone is enough, because `--cache-type radix` and `--gdn-radix` are both defaults. Unblocking overlap needs *both* PLE's lookup moved into the forward and the scheduler-ordered `clone_slot` replaced by a device-side snapshot; the device-gather alone would not do it.

**Admission.** We reserve `extend_len + max_tokens` up front and never preempt (`scheduler/prefill.py:79-92`; grep for `preempt|retract` finds only expert-cache hits). They reserve lookahead only and preempt `running[-1]`, resuming from the last align-mode checkpoint.

**Graph capture.** Ours: whole-forward capture, decode-only, keyed on `(is_decode, padded_bs)`; prefill never graphed. Theirs: a 7-field `BatchExecutionDescriptor` with FULL and PIECEWISE modes and a `splitting_ops` list that pushes `qwen4_exp_ple_short_conv` / `qsa_with_output` / `qwen_gdn_attention_core` outside the graph. We capture more of the decode step, they capture more of the workload. Both pre-size graph memory from the same bucket list the capture path uses.

**Expert residency.** Theirs is a HIP kernel inside the forward: `moe_lru_fused` decides from *this* step's `topk_ids`, rewrites the device expert→slot table and its complement, emits a miss list, and `moe_lru_gather` installs it before the GEMM reads slots — one PCIe crossing per miss, zero host sync, no inflight queue, plus a pre-gated next-layer prefetch. Ours is a host SLRU thread fed by a blocking D2H every 64 steps, with a retract/fence/copy/fence/publish handshake, and a *read-through* on miss — so a miss that also promotes crosses card 1's permanently-Gen4-x8 link twice, and k+1 times if the publish lags. Both independently settled on **pure recency** for the swap region (their `RANK_SCALE = 0.0`; our oracle: LRU 0.8558 / SLRU 0.8644 vs static-prior 0.5559, LFU 0.3597) — do not re-propose frequency-weighted eviction.

## 4. Worth adopting, ranked

Only items whose actionable survived adversarial verification. Every "measured" figure is sourced.

### Tier 1 — latent correctness, cheap, engine-side

**1. QSA raw-key ring: width and member sourcing (CONFIRMED ×2).** Their ring is `compress_ratio × cdiv(r + num_speculative_tokens, r)` wide (`qsa_cache.py:876-891`, with the comment naming the hazard), their pooling kernel sources in-forward members from raw activation rows (`use_raw = position >= chunk_start_position`, `ops/qsa.py:730-758`), and they compress *before* storing this step's rows. Ours is exactly `r` slots per request row (`attention/qsa/cache.py:57`), sources every member by residue on the non-prefill branch (`runtime.py:206-214`), and writes this forward's rows *before* pooling (`runtime.py:526` then `535`). At r=4 a verify batch of K+1 rows aliases residues, so a committed compressed key is pooled from a future — possibly rejected — token, **and** roped at the wrong first position; the corrupted key is persisted with no spec rollback. Verified reachable by launch: `_spec_decode_step` builds `phase="decode", spec_verify=True, extend_len=K+1`, `_use_static` requires `extend_len==1` so verify takes the dynamic plan, `mtp_num_hidden_layers=1` and 31 `mtp.*` tensors are in the checkpoint. Shipped default is `spec_default="none"` (`tools/serve.sh:700`), so it is latent on an operator flag — which our own rule says governs priority, not whether it is a bug. **Fix:** widen the ring to `r + max_draft` and compress-before-store (their shape), and port the raw-row member source into `QSAPlan.build`'s else-branch. `_fill_decode_plan` does **not** need it (gated on `extend_len==1`). Only observable above `indexer_budget`, so an above-budget test is required to see it.

**2. `temperature: 0` is not greedy on our server (PARTLY, actionable holds).** `core.py:165` defines `is_greedy = (temperature <= 0.0 or top_k == 1) and top_p == 1.0`, and `api_server.py:1299` fills `top_p 0.95 / top_k 20` from the served `generation_config.json` — so a bare `temperature: 0` runs the stochastic sampler at T=1e-6. Theirs normalizes at the request boundary (`sampling_params.py:543-548` forces `top_p=1.0, top_k=0, min_p=0` below 1e-5) *and* branches per row in the kernel. **The fix is in `is_greedy`, not the kernel** — per-row temperature is already a kernel arg (`sampler_kernels.hip:184/240/320`). Drop only the `top_p == 1.0` conjunct; keep `top_k == 1`. Treat it as widening a gate with five consumers (`scheduler.py:4541, 5022, 5132, 5176, 5291` — spec eligibility, greedy-vs-sampled verify, drafter capture). Note the two lanes already disagree: `spec/sampling.py:52-56` resolves `temperature <= 0` to a one-hot argmax while the plain lane emulates.

**3. Per-request counter-based RNG (CONFIRMED).** Theirs draws Gumbel noise as `murmur3_uniform32(seed, pos, token_id)` inside the argmax kernel — no RNG state, per-request seeds assigned even when the client sends none, a `_DRAFT_NOISE_SALT` so a proposal and its residual cannot share noise. Ours reads `uniform[row]` from a `torch.rand(MAX_ROUNDS, bs, generator=None)` off the global generator (`_sampler_hip.py:47`), so the linear index `r*bs+i` couples a request's token to batch width and to all prior consumption; `SamplingParams.seed` is consumed only by the canvas path (`scheduler/diffusion.py:300`). **Fix:** take `seed` + decode `position` into the op contract and hash the uniform in-kernel, keeping the tensor path as fallback. Two caveats the finding understated: the uniform is read in *two* kernels, and the spec lane's generator is per-*step* not per-request, so end-to-end seeding is wider than one kernel. `engine.py:204` does `torch.manual_seed(42)`, so a strictly-serial bs=1 replay does reproduce — the problem is coupling to traffic history, not absence of a seed.

**4. `top_p` convention, written down (PARTLY, actionable holds).** They apply top_p to the top_k-**renormalized** distribution (Triton kernel block literally headed `#### TOP-P SAMPLING AFTER TOP-K ####`); we apply it to full-vocab cumulative mass in **five** places — `sample.py:103-104`, the `_apply_top_k`/`_apply_top_p` fallback pair at `:54-67`, `topk_finalize_kernel`, `topk_topp_sampling_kernel` (the k>64 rejection path), and `spec/sampling.py:96-104`. **The verdict corrected the original claim's consequence and I am not smoothing it over:** our surviving set is always a superset of theirs and the extra tokens carry <5% of renormalized mass, so total variation is bounded ~0.05/step, and the measurement the claim cited (`api_server.py:251-257`) *isolates* this variable — the `t=1.0 + k=20 alone` arm (top_p inert) scored 0/10 corrupted, matching the both-set arm, while `p=0.95 without top_k` scored 6/10. So do **not** cite this as the junk-tool-args mechanism. The action is to document the convention and, if changing it, change all five sites in one commit behind `validate_sampled_spec`.

**5. KV calibration scales unreachable on `q4e-mxfp4` (PARTLY, actionable holds).** That repack ships 12 QSA layers of `self_attn.{q,k,v}_scale` with `kv_cache_scheme: null`; `kvcache/fp8_scales.py:151-155` returns `None` on a falsy scheme and `weight.py:1405` skips the tensors — and that directory has no `kv_scales.safetensors`, so serving it through the q4e arm runs at identity 1.0 today. Widening the gate would be **wrong**: their convention is `(max × 1.10) / divisor` with divisors Q/K=200, V=100 (`calibrate_kv.py:664`), which I corroborated numerically against our own per-head sidecar (K geomean 1.046, log-sd 0.074; V at divisor 100 geomean 0.927, at 448 it is 4.15× off). **Fix:** when shards contain `*.{k,v}_scale` but no scheme is declared, emit a *named* warning stating the divisor mismatch; and add a **read-side** metadata check — `_read_scale_file` (`fp8_scales.py:78-91`) never opens `__metadata__`, so a foreign-convention sidecar loads silently. (The write side already records `convention` and `fp8_max`.)

**6. One-line boot log for pool-truncated context (CONFIRMED).** When `num_tokens < config.max_seq_len`, name both numbers and say the context was truncated by the pool. `engine.py:2034` logs the token count and `api_server.py:2938` logs the resolved max, but the checkpoint's native length is never named.

### Tier 2 — capacity and measured-mechanism throughput

**7. Blockwise-fp8 as a WScale policy on the fp8 WMMA core (PARTLY, actionable holds).** The served checkpoint marks 12 QSA layers' q/k/v/o and 36 GDN `in_proj_qkv`/`in_proj_z`/`out_proj` as fp8 block [128,128]. I sized it from the served tree's safetensors headers: **2550 MiB fp8 → ~5100 MiB bf16, +2.49 GiB model-wide, ~1.25 GiB/card at TP=2.** Their `libfp8hip_gemm.so` serves it natively (verified at ISA level: `v_wmma_f32_16x16x16_fp8_fp8` in all three arms, plan latched per shape at weight load). The K-loop group-scale machinery already exists on our side (`tile_config.h:340-440`, `gemm_tiled.h:119-156`); what is missing is a row-block (bn=128) scale index paired with an fp8 `WLoad` — a policy on the shared core, not a new kernel. **Two constraints the original actionable omitted:** the scheme also declares dynamic per-token-per-128-K-group *activation* scales (their kernel implements them; ours is per-token epilogue), and the arm must stay M-invariant, because `Fp8BlockDequantLinearMethod` exists precisely to land on `minv_linear`'s chokepoint for chunked/prefix-cached/spec-verify bit-exactness — theirs deliberately re-plans per M bucket and is not. Correction to the dossier: the MTP head contributes **nothing** to this cost today (`spec_default="none"` zeroes `mtp_num_hidden_layers` and the loader skips every `mtp.*` key).

**8. PLE: ship raw fp8 bytes, dequant on device (PARTLY, actionable holds).** `ple/source.py:243-245` runs a 256-entry fp8 LUT on the **host** into an fp32 pinned buffer, then copies fp32 over PCIe. They memcpy the raw storage bytes and do `embeddings.to(dtype) * weight_scale` on the GPU. **The verdict inverted the motivation and I am keeping the correction:** the 4× PCIe is irrelevant (PLE moves ~61 KB/step against ~1 GiB/step of host expert streaming over the same link, and our own committed A/B measured it neutral: 17.76 / 17.57 / 17.74 tok/s, `source.py:204-208`). The real cost is host CPU — **7.1 ms per 2048-token prefill chunk, measured CPU-only on this box during verification**, serialized on the scheduler thread in `finish_rows`. Fix: pinned uint8 staging + `view(torch.float8_e4m3fn).to(dtype) * scale` on device. Expect a removed prefill host stall, *not* a TPOT change. While there, `source.py:26-31`'s "no intermediate array / avoids a second host pass" justification has been false since the async split.

**9. Dilated conv as an axis on the shared `causal_conv1d` core (PARTLY, actionable holds).** `grep -rI dilation` over all of `rdna4-hip-kernels` returns zero. Add `dilation` to `causal_conv1d_update/fwd/fwd_verify` — `hist[16]` covers PLE's 9-deep window — and route `Qwen4ExpPLE._short_conv` through it. **Two corrections:** dilation is *not* the only missing axis — `launch_causal_conv1d_fwd` reaches weight and `conv_state` through `data_ptr<float>()` (`gdn_kernels.hip:2663`) and throws on bf16, while our PLE weight and conv state are model dtype; and the value is *not* a decode lever (PLE is one decoder layer of ~48, decode is graph-captured at ~0.338 µs/node). The real prize is the per-sequence Python `F.conv1d` loop at prefill.

**10. GDN decode l2-norm: wave butterfly instead of the ceil-halving tree (PARTLY, actionable holds).** Verified in both binaries: theirs is 15 `ds_bpermute_b32` per kernel (masks 16/8/4/2/1, clamped with `v_cmp_gt_u32 32` + `v_cndmask`), two of the three butterflies purely wave-local over the 128-element head dim with zero LDS and zero barrier; static `s_barrier` tokens 8 vs our 54. **13. MXFP4 `E8m0RowRefScale` for prefill + BK widening (PARTLY, actionable holds).** Their MoE kernel folds the group exponent into the e4m3 element against a per-(expert-)row E8M0 reference; ours does an exact power-of-two fp32 fold on the accumulator each group. **The verdict flipped the sign at decode:** the fold costs `block_m × BN` FMAs per group block-wide, while folding into the element costs `BN × 32` adjustments in `stage_b` — so it wins only for `block_m > 32`, breaks even at 32, and **loses at 16**, which is what `_moe_block_m` returns at the served decode point. Also: their published "1-2e-3 rel" is attributed by their own docstrings to fp8 activation quantization vs a bf16-activation reference, not to the fold. Not bit-exact — A/B for quality.

## 5. Where we are ahead

- **Sampling.** We ship three native HIP sampler kernels; they have none — vLLM's Triton path serves, and its Qrita mask kernel runs **one program per row** at small batch (their split-row pipeline is explicitly gated off when top_k is active), exactly the bs≤6/top_k=20 shape our two-stage kernel spreads over 61 blocks. We also fence the untrained padded-vocab tail (`sample.py:334`, 243 ids on this family carrying dequant noise — their slice only removes TP padding), scrub NaN/Inf unconditionally (they only *count*, behind a default-off env), and keep the lm-head store fp32 to kill bf16 tie-ties at |logit| 16–32.
- **KV fp8 calibration.** Per-head with recorded provenance (fixture sha, per-head amax spread, TP-independent global rows); theirs is per-tensor with a 200/100 divisor. Their `q_scale` and draft-KV entries are *not* gaps for us — we never quantize Q and our MTP draft ring is bf16.
- **Kernel core policy, validated against a counterexample.** One `WLoad`-templated grouped MoE core covers int4/MXFP4-E8M0/NVFP4/fp8/int8/bf16; their `dsfp4a8` is a documented **fork** of `mxfp4a8` differing only in activation scale format, and they have no NVFP4 group-16 MoE kernel at all — the checkpoint we serve would hit their dequant emulation. Same story in offload: our residency redirect is a call-site `(base, index)` swap that every present and future format inherits (`gemv_decode.h:1870-1895`), while `offload_recipe_for` *raises* for any experts class without a hand-written recipe (exactly two exist).
- **ReplaySSM and decode fusion.** No per-step GDN state write (committed 1.13/2.60/2.90/1.50× at B=1/2/4/8), and conv + recurrence + gated RMSNorm in one decode op, bit-exact against the two-kernel path. Their decode stops at conv+recurrence and runs `RMSNormGated` separately. Our spec verify has **no qlen cap**; theirs raises above `GDN_VR_MAXQ = 9`, so a block-16 drafter cannot run on it.
- **Attention capability.** Additive `mask_bias` and a bidirectional canvas mode in the op (TiDAR block masks, DDTree ancestor masks, block-diffusion); their backend has no mask argument and declines those configs to Triton. Our dispatch fails *loudly* on an uncovered head_dim rather than silently degrading; their `rc_flash` probe latches Triton **for the process lifetime** on one unlucky first call, with only a stderr line — the exact failure that cost us a serve before we widened `_tail_hip`'s gates.
- **QSA.** Selection emitted in canonical ascending order with a total tie rule, which is what makes ≤budget sparse attention structurally bit-identical to dense and testable in place (`MINISGL_QSA_DENSE_CHECK=1`); their expansion is rank-indexed and nothing in their readable sources establishes an order. Our compressed-key addressing is `physical_slot // r` — no second allocator, prefix-shared pages give compressed reuse free.
- **Memory planning.** Measured model bytes (not a header census plus a fitted registry), no hard KV cap so context degrades instead of the boot dying, per-token-exact hybrid KV billing instead of padding every layer's page to the group max, cgroup-aware host capacity with a 12 GiB floor and a rate-gated `SwapTripwire` (their `MemAvailable`-only read is the container trap), `accounting.py`'s five checks gating the arena at `seal()`, and a prefill budget clamped against live free VRAM (theirs is static plus a hand-tuned `--kv-cache-memory-bytes`, with their own log warning it "does not respect the gpu_memory_utilization config").
- **Prefix cache granularity 16 vs 1600**, and a continuing prefill chunk losing ≤15 tokens instead of 896 of 4096.
- **CPU-compute expert tier.** `StackKind.CPU` computes whole MoE layers on the host; their cold path is always a device read over PCIe — which on card 1's permanently Gen4 x8 riser is the expensive direction.
- **fp8 convert.** Four VALU ops (one `v_med3_num_f32` + one hardware `v_cvt_pk_fp8_f32` + a multiply by a pre-inverted reciprocal) against their ~38-op software ISA transcription plus a full IEEE divide, engine-wide. Keep it. (One caveat to record: our `med3` lowering returns the non-NaN operand, so a NaN activation stores −448 rather than propagating.)
- **Shape-template + launch-bounds discipline.** `gdn_prefill_wmma` is 0 spill / 0 scratch; their heaviest chunk-state stage spills. `dense_gemm_pipe_kernel` already carries a tight truthful `__launch_bounds__(256)`, which is exactly the lever 100 of their 110 dense GEMM kernels are missing.
