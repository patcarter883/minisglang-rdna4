# Spec-decode modes review — 2026-08-25

Multi-agent workflow review of all speculative-decode modes (ngram, MTP, EAGLE3, DFlash, DSpark, TiDAR, DDTree) plus cross-cutting machinery (acceptance/sampling, capture/width, scheduler integration, config/serve consistency).

Process: 10 dimension reviewers -> one adversarial verifier per finding (instructed to REFUTE). 57 raw findings; 3 refuted and dropped; **54 survived, 53 CONFIRMED** (verifier independently traced the defect in code), 1 PLAUSIBLE. A second verification pass (2026-08-25 evening) covered the 16 findings whose original verifiers hit a rate limit: 15 confirmed, 1 refuted (sampled DDTree greedy-walk — deliberate documented design, see docs/SAMPLED_SPEC_VERIFY.md).

Severities shown are post-verification (verifiers could downgrade/upgrade).


## Per-dimension verdicts

### ngram

The ngram proposer's matching core is correct: window fallback order (max->min), needle self-exclusion and the follow-token boundary are all handled right, short/empty histories return cleanly, the per-req clamp to remain_len-1 is sound, and it composes correctly with greedy, sampled (deterministic-proposal rejection sampling is the right scheme for a model-free drafter), and constrained acceptance; batch gating is consistent though the ngram=0 (never gate) default is an explicitly unmeasured assumption borrowed from MTP. The material performance hole is the miss path: an all-empty-draft step falls to the eager verify forward instead of the captured plain-decode graph — on non-repetitive text that is the majority of steps, so ngram mode likely underperforms SPEC=none despite the doc claiming graceful degradation. Secondary costs are the O(L)-per-step full-history rescan (with a gratuitous int32->int64 full copy) on the host hot loop, and a narrow but real staging overflow where width padding can index past the page-table columns for max-context requests.

### mtp

The MTP self-speculation proposer is implemented to a high standard on the axes that matter: the propose forward is CUDA-graph captured at boot on bucketed batch sizes with honest engagement counters, the hot loop has exactly one D2H sync per step (drafts readback) and one pinned H2D for staging, the draft-KV ring genuinely fixes the old past-8192 silent no-op (absolute-position masking, unbounded context at fixed 3 MB), TP lockstep is sound (deterministic host staging, in-head collectives, rank0 draft broadcast plus rank0-authoritative accept), and serve.sh's k_mtp flows through --spec-num-draft into the unrolled K-step chain, with the measured bs-gate deliberately left off for MTP. The defects found are both in the prompt-seed conventions: seed_prefill was never taught the cached_len origin the scheduler now feeds it on prefix-cache hits (seeding actively wrong K/V on exactly the multi-turn traffic where seeding is supposed to pay), and the ring conversion introduced a one-pair collision between the seed's position-indexed columns and decode's count-indexed columns. Little performance is left on the table in this file; the propose cost is dominated by the (algorithmically required) per-chain-step full-vocab lm_head, not by avoidable host overhead.

### eagle3

The EAGLE3 proposer is structurally sound and unusually well-instrumented: propose is genuinely CUDA-graph captured through the shared CapturableProposer (boot-time bucketed capture, honest engagement stats), the hot loop holds the one-D2H-sync-per-step invariant (Req.input_ids is CPU, drafts leave via a single .cpu()), the d2t draft-to-target remap stays on-device inside the captured chain, the 3-layer aux capture point for GLM-4.7-Flash is correct (x+residual after layers [1,22,43] == SGLang's layer-input at [2,23,44]), and batch-gating (max_bs=1) plus accept (target-vocab ids through the proposer-agnostic sampled/greedy verify) are consistent. The defects concentrate in the prompt-prefill draft-KV seeding lever (+8.5% measured): it is misaligned for radix prefix-cache hits — the dominant multi-turn production traffic, which the scheduler explicitly opted into on an assumption only DFlash satisfies — and carries a seed-to-decode cursor off-by-one that clobbers the last prompt token's draft KV on every seeded request; both bugs are shared with the MTP mirror. Remaining perf on the table is minor: a redundant full-tail aux clone per seeded prefill (missing prefill_aux_tail=1), a stale-aux first step after concurrency transitions, and the eagle3 bs-gate crossover plus the 512-token KV window still being unmeasured for this drafter.

### dflash-dspark

The DFlash/DSpark implementation is correct in the places most likely to be wrong: the [anchor, mask*(B-1)] block assembly and the markov-shifted vs in-place row alignment match between the eager and captured paths (with the last-position forfeit documented and deliberate); the modulo-ring's absolute-position mask, rebuild-gap coverage (gap<=block always re-projected by the fixed A-tail), NULL-slot padding, and slot free-list are all sound; FULL_CAP is enforced on the captured ring and on the scheduler's aux cap on every init path; and _conf_cut preserves the accepted-prefix invariant with capture-safe static _g_conf writes. Where performance is left on the table is concentrated in DSpark: the shipped default tau=0.5 is the measured-worst setting at the only batch size the default spec gate allows (~10% loss vs tau=0), the sequential Markov walk streams ~51 MB of markov_w2 plus a full-vocab argmax per block position (~300 MB/step at block 7) when a top-C candidate re-score would cost kilobytes, and the confidence path adds a second per-step host sync plus dead in-graph compute at tau=0 — together a large share of the overhead behind the measured M=1 net-negative. One latent correctness hazard: the compressed-vocab (d2t) drafter combination with the DSpark heads indexes markov_w1 with target-vocab ids (and captured/eager disagree pre/post-remap), which nothing refuses at load; and the ring's memory-refusal fallback reintroduces unbounded per-uid KV growth for full-attention drafters on exactly the memory-starved boxes.

### tidar

The fused TiDAR core math is correct: the tidar_mask.py predicate gives verify rows strictly causal visibility (no replica/mask leakage into S or the confirmed row, in both flat and segmented layouts), §7.6 RoPE positions are right, draft/replica KV is rolled back page-consistently with allocate_paged, CCA accepted-prefix state install is correctly indexed, and sampled requests are correctly excluded (greedy-only verify enforced at line 791-794). The serious gap is expert parallelism: three independent defects (unaccounted bootstrap forward, un-gated fused graph replay, and a scheduler graph-veto the engine ignores) each wedge a DP+EP serve on essentially the first request, and GDN backbones have neither metadata plumbing nor a guard. On performance, graph capture of the fused forward exists and engages, but the exact-batch-size gate leaves the dominant forward eager at in-between concurrencies, and the commit loop pays 2 host syncs per request per step plus a doubled per-req device-side mask build on the flat path.

### ddtree

The pure tree math in ddtree.py is solid: build_draft_tree is a correct best-first frontier enumeration, the ancestor masks (dynamic, baked-template, segmented, fused) are mutually consistent, position-ids are depth-correct, and the classic tree-spec KV-compaction bug is structurally avoided by making the tree verify throwaway (snapshot/restore + page free) and committing through the proven linear verify — so greedy output is lossless by construction, and TP safety of the base path is handled via the existing draft/accept broadcasts. The cost of that safety is the mode's main problem: every step pays a second full target forward (F3) that is additionally almost always eager because ddtree_drafts is excluded from the captured-width padding, so the dominant cost of the step forfeits both the compaction win and graph capture. Real correctness holes remain at the edges: unclamped tree_qlen staging crashes deterministically near the context limit, the FUSE path can desync TP ranks, and recurrent backbones are only partially honest (CCA needs opt-in SEG; GDN tree logits are silently invalid with no gate). Nothing is wired into serve.sh/SPEC_DECODE.md yet, consistent with an experimental correctness-first v1.

### accept-sampling

The acceptance machinery itself is implemented correctly: greedy chain/first-mismatch/bonus semantics match between accept.py and the vectorized accept_gpu.py (whose gating — single-EOS, unconstrained, ungated, unpadded, greedy-only — is complete and consistent), the deterministic-proposal rejection sampling in sampling.py preserves the target distribution including the degenerate residual case, and the past TP desync class is properly closed by _bcast_accept_tp making rank0's outcome authoritative. The high-stakes gap is that the entire spec verify lane bypasses the Sampler's logit-processing stack — padded-vocab fence, NaN scrub, penalties, and min_p are all silently dropped, so spec output diverges from plain decode exactly where the code claims losslessness. On performance, the sampled paths (verify_sampled and especially the constrained variant) are host-serial with multiple syncs per request/position — the classic per-step sync antipattern the greedy on-device chain was built to eliminate, left unaddressed on the sampled traffic that MINISGL_SPEC_SAMPLED targets.

### capture-width

The verify-capture machinery is implemented correctly: the past page-table-width-at-capture bug's fix pattern (max-width static tables with constant stride, kernel reads bounded by cache_seqlens) holds at all four verify capture sites (hip K+1, fused, ddtree, MLA); replay copies every dynamic input I could enumerate (input_ids/out_loc/positions via copy_from, cache_seqlens/page_table/SWA rings/GDN/CCA state indices via prepare_*_for_replay, cu_seqlens_q static by construction); widths share one buffer/pool captured widest-first, and eager fallbacks are instrumented rather than silent. Contrary to the briefed gap, the width rule now DOES have a batch-size term (width_cap's deterministic 32-row budget, TP-safe) and adapts per step from a censoring-corrected survival estimator. The performance left on the table is: graph/buffer over-capture versus the spec batch gate (VRAM that shrinks the KV pool), a downward bias in the survival estimator on ragged/empty-draft steps that narrows the width below optimum, the all-empty-drafts step falling to a fully eager forward, and the DP+EP path pinning the widest rung where the measured bs=8 optimum is the narrowest.

### scheduler-integration

The scheduler integration of spec decode is substantially well-engineered on its main path: the batch gate is checked before any work, drafts and accept outcomes are made rank0-authoritative before commit, KV/recurrent-state rollback is page-aware and consistent with next-step re-allocation, and the adaptive width always lands on a captured graph. The real defects live at the seams between modes: the DP+EP captured lockstep can wedge on an all-empty-draft step (eager vs captured MoE collectives), per-uid GPU hidden buffers leak for every request that finishes off the spec path, the reasoning-gate accept branch mishandles genuine EOS under an unbounded think budget (the live Qwen3.8+DSpark config), and the fused-TiDAR step skips grammar/think-gate enforcement and TP lockstep entirely. Performance is mostly left on the table in small per-step host costs (multiple D2H syncs on the on-device accept, serialized gloo broadcasts) and in the EP loop's missing prefill seeding, which depresses drafter acceptance under DP+EP.

### config-serve-consistency

The spec configuration layer is structurally sound: SPEC names are validated consistently at all three layers (serve.sh case statement exits 2 on a typo, argparse choices match SPEC_ALGORITHMS plus none, SpecConfig re-validates), SPEC=dspark maps correctly to --spec-algorithm dflash with proposer-side head detection, k defaults agree between code (spec_num_draft=4) and serve.sh's table, and every forwarded env var reader I checked is empty-string-safe against compose's ${VAR:-} substitution. The real gaps are at the seams: the compose lean-env anchor defaults MINISGL_SPEC_MHA_PAGED=1 while the engine documents that path as opt-in-pending-validation with a shipped default of 0 (every non-MLA spec serve silently runs it); the dspark alias misses the dflash mem-ratio/quant guards on three model arms so SPEC=dspark reproduces the documented num_pages boot assert; and the eagle3 env-knob family recreates the known missing-passthrough trap that MINISGL_DFLASH_BLOCK already had fixed for its sibling. Performance left on the table is modest and mostly about unreachable or un-encoded tuning points (dspark's validated MINISGL_SPEC_MAX_BS=4 and tau interplay, the verify row-budget knob) rather than wrong hot-path defaults.


## Findings (ranked by severity, confirmed first)

### 1. [HIGH/CONFIRMED] python/minisgl/spec/mtp.py:287 (mtp, correctness)

**seed_prefill assumes last_hidden covers prompt positions 0..P-1, but on a radix prefix-cache hit the scheduler passes only the SUFFIX rows [cached_len, cached_len+ext), so the draft KV is seeded from misaligned (token, hidden, RoPE) triples.**

- **Failure scenario:** Multi-turn request hits the prefix cache with cached_len=C>0 and suffix length L. Scheduler._spec_prefill_seeded (scheduler.py:3010-3061, whose comment explicitly says prefix-cache hits are now seeded and that 'the consumer derives its origin as cached_len - P' — true only for the DFlash consumer) hands seed_prefill lh of shape [L]. seed_prefill sets P=L and seeds pairs from tokens req.input_ids[1:L] (the START of the prompt, absolute indices) at RoPE positions 1..L-1, paired with suffix hiddens for absolute positions C..C+L-2. Every seeded K/V entry is wrong in token, hidden, and rotary phase, yet passes the ring mask (labels 1..L-1 <= qa), so the drafter attends to garbage keys for roughly the first ring-window (~512) tokens of the response. Accept rate collapses toward zero on exactly the cached-prefix/multi-turn traffic while still paying propose + verify(K+1) per step — a silent, unlogged throughput regression (output stays correct because verify gates every token). This is the 'fix lands on one sibling only' pattern: the cached_len-origin handling was added for DFlash aux seeding but never to MTPProposer.seed_prefill.
- **Suggested fix:** Derive the absolute origin the same way DFlash does: A = req.cached_len - P (cached_len has already been advanced by complete_one when seed_prefill runs). Seed pairs p in [max(A+1, A+P-ring) .. A+P-1] using tokens req.input_ids[p], prev_hidden lh[p-1-A], RoPE positions p, ring columns/labels from the absolute pair index, and set the cursor to the pair index following the last seeded pair. Add a parity/regression test that seeds with cached_len>0 and asserts byte-equality against an unchunked cold seed of the same full prompt.
- **Verifier:** MTPProposer.seed_prefill (mtp.py:277-302) derives everything from P = last_hidden.shape[0] and never reads req.cached_len: it seeds tokens req.input_ids[p_lo:P] (prompt-start absolute indices) at RoPE positions arange(p_lo,P), paired with suffix hiddens, while decode-time stage_propose/propose_body use absolute positions base = req.cached_len (mtp.py:196, 234) — so with cached_len=C>0 every seeded K/V is off by C in token, hidden pairing, and rotary phase. The scheduler deliberately seeds prefix-cache hits (scheduler.py:3012-3019 removed the cached_len==0 guard, justifying it only via DFlash's ctx_start = cached_len - P in dflash.py:1447/1487), the path is default-on (supports_prefill_seed=True, scheduler.py:551), seed_prefill registers slot_uid so the first propose keeps the bad seed instead of resetting cold (mtp.py:301, 188-193), and the ring mask (mtp.py:240) exposes all seeded columns. Verify gates output so this is a silent accept-rate/throughput regression on multi-turn cache-hit traffic, decaying only as garbage ages out of the 512-entry ring.

### 2. [HIGH/CONFIRMED] python/minisgl/spec/draft_model.py:363 (eagle3, correctness)

**seed_prefill assumes the aux/hidden slice starts at absolute position 0, but for radix prefix-cache hits the scheduler passes only the suffix rows [cached_len, cached_len+ext), so tokens, aux pairing, RoPE positions, ring labels and cursor are all misaligned for any seeded request with cached_len>0.**

- **Failure scenario:** Multi-turn GLM-4.7-Flash agent traffic (production EAGLE3 config): a request with a 25k-token cached system prefix and a 100-token new turn passes the seed gate (extend_len=100 <= MINISGL_SPEC_SEED_MAX_PROMPT=512) and enters _spec_prefill_seeded, which was explicitly changed (scheduler.py:3012-3024) to include cache hits on the claim that 'the consumer derives its origin as cached_len - P' — true for DFlash but NOT for this seed_prefill. Here P = aux.shape[1] = 100, so it seeds pairs (input_ids[1..99] — tokens from the START of the old system prompt) with aux rows that actually belong to positions C..C+98, rotated at RoPE positions 1..99 instead of C+1..C+99, and sets the cursor to 99 while the first propose queries from position C+100. The draft KV for exactly the highest-value traffic (short deltas on cached prefixes) is garbage — worse than a cold cache, so accept-len collapses toward the ~2% floor for those requests while propose + K=6 verify are still paid every step. E2e text stays correct (verify gates), so nothing crashes or logs; it is a silent throughput loss. Same defect exists in the mirror MTPProposer.seed_prefill (mtp.py:277-302).
- **Suggested fix:** Derive the origin like DFlash does: at call time req.cached_len has been advanced to the full prompt length by complete_one, so origin = req.cached_len - P (assert >= 0). Seed absolute pairs p in [max(origin+1, req.cached_len - self._ring), req.cached_len): tokens = req.input_ids[p], fused from aux[:, p-1-origin], positions = p, pos_buf labels = p, and set the cursor from the absolute end (see next finding). Apply the identical fix to MTPProposer.seed_prefill.
- **Verifier:** scheduler.py:3012-3024 includes cached_len>0 reqs in the seed plan, passing suffix-only slices [cached_len, cached_len+ext), justified by DFlash's `ctx_start = cached_len - P` (dflash.py:1447) — but DraftModelProposer.seed_prefill (draft_model.py:363-393) never reads cached_len: it sets P = aux.shape[1] and seeds tokens req.input_ids[p_lo:P] (prefix-START tokens) paired with aux rows of absolute positions C..C+P-2, at RoPE positions 1..P-1 and pos_buf labels 1..P-1, cursor = P-1. The _spec_seed_fits gate (scheduler.py:2975) checks only extend_len so the 25k-cached/100-new case passes, _ctx_gate defaults to 1<<62 so the req still proposes, and the absolute-position mask (draft_model.py:328) keeps the mislabeled columns visible — worse than cold (cold columns are -1 = masked). MTPProposer.seed_prefill (mtp.py:277-302) has the identical zero-origin assumption and also takes this path (supports_prefill_seed=True). Output text stays correct (verify gates), so this is a silent accept-rate/throughput defect on exactly the cache-hit traffic the seed was extended to cover.

### 3. [HIGH/CONFIRMED] python/minisgl/scheduler/scheduler.py:3634 (tidar, correctness)

**The fused-TiDAR bootstrap block_predict issues a second full-target EP-collective forward that the EP lockstep does not account for (_spec_num_ep_forwards returns 1 for fused), desyncing the per-layer MoE collectives across DP+EP replicas.**

- **Failure scenario:** Serve with SPEC=tidar, MINISGL_TIDAR_FUSED=1, --enable-ep (DP+EP). Any step where a replica has a req with _tidar_drafts=None (i.e. the FIRST spec step of every request) makes that replica run 2 full-target forwards (bootstrap _tidar_block_predict at line 3634 + the fused forward at 3731) while the idle replica issues n_ep=1 dummy forward (line 2937-2940) and another busy replica without fresh reqs issues 1 — the per-layer MoE all_gathers pair off-by-one and both ranks wedge (one blocked in a GPU collective, the other in the next loop's CPU all_reduce).
- **Suggested fix:** Fold bootstrap into the lockstep: add a local_has_fresh flag to the all_reduced tensor in _spec_ep_loop; when any replica reports fresh reqs, every replica without them issues one extra dummy _tidar_block_predict (skip_alloc) before/after its step. - **Verifier:** Traced fully in code: _spec_num_ep_forwards returns 1 for fused TiDAR (scheduler.py:2783) and the idle EP replica issues exactly n_ep=1 dummy _tidar_block_predict (2937-2940), but _spec_decode_step_tidar_fused runs a bootstrap _tidar_block_predict (3632-3636, a full-target forward_verify at 3195 that issues per-layer EP MoE collectives) plus the fused forward (3731) whenever any req has _tidar_drafts=None — which is every request's first spec step, since nothing outside the fused/two-forward steps ever seeds _tidar_drafts. The lockstep all_reduce tensor (2827-2830) carries no fresh-req bit, and fused mode forces the eager self-agreed-N regime (_ep_spec_common_verify_bs returns None at 2955), which equalizes token counts within a collective but cannot reconcile a mismatched number of collective calls — so one rank blocks in its second forward's MoE all_gather while the other blocks in the next loop's CPU all_reduce: a hard wedge. No guard rejects MINISGL_TIDAR_FUSED=1 with --enable-ep. High (not critical) because it is confined to the fused-TiDAR + DP/EP configuration, where it deadlocks deterministically.

**can_use_fused_verify has no EP gate, unlike the DDTree replay directly below it (line 1446, 'and not self.enable_ep'), so under DP+EP the busy replica replays the fused graph with a baked fixed-N MoE all_gather while the idle replica runs eager self-agreed-N dummies.**

### 5. [HIGH/CONFIRMED] python/minisgl/scheduler/scheduler.py:3449 (ddtree, correctness)

**Under TP>1 with MINISGL_DDTREE_FUSE=1, the on-path decision (req._ddtree_fused_next, set per rank from the rank-local tree walk at scheduler.py:3395-3409) can diverge across TP ranks, so fused_reqs/need_f1 partition differently and _tidar_block_predict issues a different forward (different lm-head all_gather row count, or no forward at all on one rank).**

Same class as the fixed sampled-accept TP desync, reintroduced on the fuse path.
- **Suggested fix:** Make the on-path outcome rank0-authoritative: broadcast a per-req on_path bit (and the reused top-K marginals, or recompute them from broadcast row indices) over tp_cpu_group before storing _ddtree_fused_next, mirroring _bcast_drafts_tp/_bcast_accept_tp; or gate MINISGL_DDTREE_FUSE off when tp_size > 1.

Next step, need_f1 partitions on that rank-local attribute (3449-3451) and `if need_f1:` gates _tidar_block_predict (3452-3453), a full target forward with per-layer TP all_reduce and a batch-sized lm-head all_gather — empty-vs-nonempty (or different-sized) need_f1 across ranks means one rank skips or mis-sizes a collective the other joins, the exact hang/illegal-address class _bcast_drafts_tp documents (3971-3976). The linear commit path is protected by _bcast_drafts_tp/_bcast_accept_tp (4140, 4476), confirming the fused bit is the one control-flow divergence lacking the established rank0-authoritative broadcast; severity stays high (not critical) only because MINISGL_DDTREE_FUSE is an experimental opt-in env var absent from serve.sh's validated operating points.

### 6. [HIGH/CONFIRMED] python/minisgl/scheduler/scheduler.py:4163 (ddtree, performance)

**The DDTree commit forward (F3) explicitly skips pad_to_captured_width (`if not ddtree_drafts`), and the accepted-path length varies per step (0..L), so extend_len almost never equals a captured verify width and the commit runs the EAGER full-target verify nearly every step.**

The mode fails the graph-capture-required bar while its F2 graph machinery sits unused for the bigger forward.
- **Suggested fix:** Let ddtree_drafts take the same pad_to_captured_width path (pad the accepted path with filler to the nearest captured rung; the accept loop already slices by real per-req draft length, and the padding comment itself proves losslessness), keeping the on-device-accept exclusion as is.
- **Verifier:** scheduler.py:4161-4163 provably skips pad_to_captured_width when ddtree_drafts=True, and F3 stages extend_len = len(accepted path)+1 (scheduler.py:4189, core.py:210), which varies per step. graph.py:581-593 (can_use_verify_graph) requires extend_len to be exactly a captured qlen from the halving ladder (spec/width.py:141-168, e.g. [2,4,8] for K=8), so any step whose accepted path length is off-ladder runs the full-target verify eager (scheduler.py:4231-4237); only the F2 tree-verify has a dedicated captured graph (capture_spec_ddtree_verify_graphs), and tools/ddtree_capture_ab.sh validates F2 capture while F3 has no capture or padding path at all.
